Миграции Django: от модели к таблице

Что создаёт базу, что записывает инструкцию, а что выполняет её. Команды ниже запускаются в своём учебном проекте.

Первый migrate: что сейчас произойдёт

Миграция — сохранённая инструкция изменения структуры базы: например, создать таблицу или добавить поле. Python-файл модели описывает желаемые данные, файл миграции описывает изменение, а таблица находится в самой базе. Ниже сохранён прежний полный разбор этой цепочки.

В Django уже есть приложения auth (учётные записи и права), admin (в том числе журнал действий админки), contenttypes (учёт типов моделей) и sessions (сеансы). Если они подключены в INSTALLED_APPS, их готовые миграции поставляются вместе с Django. Поэтому первый migrate можно выполнить без предварительного makemigrations: инструкции для этих приложений уже написаны разработчиками Django.

1. Применить готовые инструкции

Терминал VS Code рядом с manage.py
python manage.py migrate

Ожидаемый результат В терминале перечислены приложения и строки вида Applying contenttypes.0001_initial... OK, Applying auth.0001_initial... OK. Набор и порядок зависят от проекта и уже выполненных миграций. Если всё применено раньше: No migrations to apply.

Команда читает настройки текущего проекта и работает с подключением DATABASES['default']. Перед запуском сверь локально ENGINE='django.db.backends.postgresql' и NAME='catalog_db', а также свою роль и адрес сервера. Успех в другом подключении, например SQLite, не подтверждает работу нужной PostgreSQL. Значения паролей не выводи.

2. Посмотреть, что отмечено применённым

Тот же терминал; команда только показывает статус
python manage.py showmigrations

Ожидаемый результат Названия приложений и миграций: [X] означает применённую миграцию, [ ] — ещё не применённую. У нового catalog пока может быть (no migrations): модель Product добавим следующим этапом.

Четыре команды — разные результаты

Мы же уже писали CREATE TABLE и ALTER TABLE?

Да: раньше вы вручную писали SQL-инструкции, например CREATE TABLE для создания таблицы и ALTER TABLE для изменения. С Django база остаётся PostgreSQL, а изменения по-прежнему исполняются через SQL. Меняется способ подготовки и учёта этих изменений.

Цепочка: models.py описывает модель → makemigrations записывает операции изменения в Python-файл миграции → migrate применяет их через SQL к PostgreSQL и учитывает применение. Файл миграции обычно содержит операции Django, а не просто готовый SQL-текст; нужный SQL формируется для выбранной базы при выполнении.

CREATE DATABASE отдельно создаёт саму базу. Обычный migrate её не создаёт: он подключается к уже существующей базе из настроек и меняет структуру внутри неё.

Позже, после makemigrations catalog: посмотреть SQL

Показать SQL первой миграции catalog

Только когда catalog/migrations/0001_initial.py уже появился
python manage.py sqlmigrate catalog 0001

Ожидаемый результат SQL для этой миграции, например CREATE TABLE. Вывод смотрим в терминале.

sqlmigrate показывает SQL и ничего не применяет. Чтобы выполнить операции миграции, используется migrate. На первом системном migrate собственной миграции catalog ещё может не быть — эту команду пока пропусти.

Где находятся файлы, таблицы и учёт

  • Файлы своего приложения: папка catalog/migrations/ рядом с catalog/models.py. Сразу после startapp в ней обычно только __init__.py. Файл 0001_initial.py появится после создания модели и команды makemigrations catalog, а не после первого системного migrate.
  • Встроенные файлы: внутри установленного пакета Django выбранного Python, например …/site-packages/django/contrib/auth/migrations/. Копировать их в catalog не нужно.
  • Таблицы: на сервере PostgreSQL в выбранной базе catalog_db, а не в папке Python-проекта. Если смотришь через pgAdmin, открой именно эту базу → Schemas → public → Tables и обнови список. В этом маршруте отдельную схему не создаём. Среди таблиц будут, например, auth_user, django_session и django_migrations.
  • Учёт применения: таблица django_migrations хранит записи о применённых миграциях для этой базы: приложение, имя миграции и время применения. Это не таблица товаров. Файлы инструкций и записи об их применении — разные вещи.

Что означает повторный запуск

Обычный повторный migrate без дополнительных аргументов применяет только недостающие миграции с учётом их зависимостей. Если новых нет, сообщает No migrations to apply. Он не запускает веб-сервер и не добавляет товары. В нашем первом запуске применяются встроенные инструкции Django; будущий Product появится отдельным шагом. Вообще миграции могут также содержать специально написанные операции с данными, но таких инструкций добавления товаров в этом маршруте нет.

Если появилась ошибка, читай последнюю строку в этом же терминале и сохраняй её для вопроса преподавателю. Отметку успеха ставь после успешного завершения и проверки нужного подключения. Ни вывод check, ни сохранённые галочки пульта не заменяют эту проверку.
