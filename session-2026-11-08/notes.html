Что получилось на занятии

8 ноября сделали первый экран каталога: товар из базы на главной странице. Добавили товар через админку Django, прочитали его в Python и вернули браузеру текстовую строку. Это минимальный экран каталога без HTML-шаблонов и фильтров.

Здесь разобрана Django-часть занятия. Проверку цены и сохранения после перезапуска выполни в закреплении.

Четыре разных вещи

Модель — catalog/models.py
Описание данных в Python: у товара есть название и цена.
Миграция — catalog/migrations/
Сохранённая инструкция изменения структуры базы, например создания таблицы.
Таблица — в базе данных
Место для записей. Для Product стандартное имя — catalog_product.
Запись — один товар
Например, «Тетрадь» с ценой 80.00. Добавление записи не меняет структуру и не требует новой миграции.

Цепочка: модель → makemigrations → инструкция → migrate → таблица → добавление товара → запись → home → ответ браузеру.

1. Где находится проект

Открой в VS Code папку проекта, с которым работал на занятии. Неважно, на чьём GitHub хранится репозиторий: для выполнения заданий нужна копия файлов на твоём компьютере. Новый git init не нужен. Команды Django вводи в терминале VS Code с активным учебным окружением Python.

Если дома нет проекта или доступа к репозиторию

Попроси тьютора дать ссылку на нужный репозиторий и ветку либо архив твоего проекта. Если код находится в общем репозитории, нужна именно та ветка, в которой ты работал.

Если ссылка открывается в браузере: выбери указанную тьютором ветку → Code → Download ZIP, распакуй архив в отдельную папку и открой её в VS Code. Для скачивания открытого репозитория вход в GitHub не нужен; если доступа нет, получи архив у тьютора. Доступ на запись и отправка изменений на GitHub для этих заданий не требуются.

Архив с кодом не гарантирует, что дома уже есть база, товары и пользователь админки. Подключение, миграции и вход проверяются отдельно в следующих шагах. Если файлами пока не располагаешь, можно читать разбор и отвечать на вопросы; запуск и сохранение товара считаются выполненными после проверки в своём проекте.

В примере внешняя папка mysite содержит manage.py, а внутренняя mysite — настройки и маршруты. Если внутренняя папка называется config, то mysite/settings.py соответствует config/settings.py, а mysite/urls.py — config/urls.py.

python-calculator/       ← существующий репозиторий
└── mysite/              ← рабочая папка команд
    ├── manage.py
    ├── catalog/         ← приложение каталога
    └── mysite/          ← или config: настройки проекта
Если Django-проекта ещё нет

Только если восстанавливаешь пример с нуля: создай отдельную учебную папку, открой её в VS Code и выполни команды ниже из неё. Если работаешь внутри уже скачанного репозитория, используй его папку. Если manage.py уже есть, открой его папку и пропусти создание. Существующий проект не перезаписывай.

python -m django --version
python -m django startproject mysite
cd mysite
python manage.py runserver

Первая команда проверяет Django. Остальные создают проект, переходят в его папку и запускают сервер. В браузере открой http://127.0.0.1:8000/: должна появиться стартовая страница Django. Если модуль Django не найден, выбери учебное окружение и установи зависимости своего проекта.

2. Приложение catalog и главная

Терминал рядом с manage.py. Если приложения ещё нет, создай его:

python manage.py startapp catalog

Появится папка catalog. В mysite/settings.py добавь "catalog", в существующий список INSTALLED_APPS, сохрани остальные приложения. Так Django узнаёт о каталоге.

В catalog/views.py функция home отвечает на запрос главной. Финальная версия с чтением товара приведена в шаге 6. Сохраняй файлы через Ctrl+S.

3. База и первый migrate

В примере используется PostgreSQL и база catalog_db. Если твой проект уже выводит товар на главную, сохрани его рабочие настройки подключения. Имя базы можно посмотреть в settings.py, в разделе DATABASES, поле NAME.

catalog_db может уже быть на том компьютере, где её создавали на занятии. На домашнем компьютере её может не быть: скачивание кода с GitHub не создаёт базу PostgreSQL.

Если настраиваешь пример дома, открой SQL Shell (psql) и подключись к своему PostgreSQL. Команда \l показывает список баз. Если в нём есть catalog_db, повторно создавать её не надо. Если её нет, выполни:

CREATE DATABASE catalog_db;

Ожидается CREATE DATABASE. Если база уже существует, повторять создание не надо. В settings.py у подключения PostgreSQL ENGINE — django.db.backends.postgresql, NAME — catalog_db; пользователь, пароль, адрес и порт должны соответствовать твоему локальному серверу. Сохрани рабочее подключение; не публикуй пароль.

migrate применяет готовые миграции — инструкции изменения базы. При первом запуске создаёт служебные таблицы Django, в том числе для пользователей и сеансов. В отличие от CREATE DATABASE, эта команда работает внутри уже выбранной базы.

Терминал рядом с manage.py:

python manage.py migrate

Ожидается список применений с OK либо No migrations to apply, если всё уже применено. Готовые инструкции служебных приложений входят в Django.

4. Модель Product → таблица

Файл catalog/models.py. Пример модели с названием и точной десятичной ценой. Если Product уже есть, сначала сравни поля со своим кодом, не создавай второй класс.

from django.db import models

class Product(models.Model):
    name = models.CharField(max_length=100)
    price = models.DecimalField(max_digits=10, decimal_places=2)

CharField хранит строку до 100 символов. DecimalField хранит число до 10 цифр всего, из них 2 после точки. Сохрани файл, затем в терминале рядом с manage.py:

python manage.py makemigrations catalog
python manage.py migrate
python manage.py showmigrations catalog

makemigrations записывает инструкцию по изменениям модели; migrate применяет её к выбранной базе; showmigrations проверяет применение. У миграции приложения должен стоять [X]. Если модель не менялась, No changes detected — нормально.

Разобрать эту цепочку подробнее: готовое объяснение миграций.

5. Админка → запись товара

Файл catalog/admin.py:

from django.contrib import admin
from .models import Product

admin.site.register(Product)

Регистрация делает Product доступным в админке. Саму таблицу она не создаёт. Если регистрация уже есть, повторно её не добавляй.

Файл mysite/urls.py (или config/urls.py). В существующий список маршрутов добавь недостающее. Ниже схема: прежние about/, contacts/ и их импорты сохрани. Если маршрут "" уже есть, замени его обработчик на home, не дублируй маршрут.

from django.contrib import admin
from django.urls import path
from catalog.views import home

urlpatterns = [
    path("admin/", admin.site.urls),
    path("", home, name="home"),
    # Здесь сохраняются прежние маршруты about/ и contacts/.
]

Терминал рядом с manage.py:

python manage.py createsuperuser

Создаёт пользователя админки в выбранной базе. Введи своё имя, email по запросу и надёжный пароль дважды. В терминале символы пароля не показываются. Дождись Superuser created successfully. Если пользователь уже создан и вход работает, повторять не нужно.

python manage.py runserver

Открой http://127.0.0.1:8000/admin/, войди, выбери Products → Add, введи название и цену, нажми Save. Ожидается сохранённая запись товара.

6. Товар из базы → главная страница

Файл catalog/views.py. Добавь импорты и обнови только home; функции прежних страниц сохрани.

from django.http import HttpResponse
from .models import Product

def home(request):
    product = Product.objects.order_by("-id").first()
    if product is None:
        return HttpResponse("Пока нет товаров", content_type="text/plain; charset=utf-8")
    return HttpResponse(
        f"{product.name} — {product.price} руб.",
        content_type="text/plain; charset=utf-8",
    )

Product.objects позволяет обращаться к таблице через модель. В этом учебном варианте order_by("-id").first() берёт последний добавленный товар, поэтому новый товар из закрепления будет виден на главной. Если записей нет, показывается понятное сообщение.

HttpResponse возвращает текст браузеру. content_type указывает, что это обычный текст: название товара не интерпретируется как HTML.

Сохрани файл, открой http://127.0.0.1:8000/ и обнови страницу. Пример результата: Тетрадь — 80.00 руб. У тебя будут свои название и цена. Проверка сохранения после перезапуска — в обязательном закреплении.

Если что-то не работает

Не удаётся импортировать home
Проверь имя функции в catalog/views.py и сохрани файл. Импорт в urls.py должен указывать на неё.
HttpResponse is not defined
Импорт HttpResponse нужен именно в catalog/views.py. Импорт в другом файле сюда не переносится.
404 на /admin/
Проверь path("admin/", admin.site.urls) и импорт admin в основном urls.py.
Таблица не существует / неприменённые миграции
Убедись, что терминал открыт у нужного manage.py и выбрано рабочее подключение. Выполни migrate; для Product проверь makemigrations catalog и showmigrations catalog.
Пользователь не найден / вход не работает
Проверь выбранную базу. Пользователь должен существовать именно в ней. При необходимости создай createsuperuser в этом проекте; пароль в переписку и код не вставляй.
На главной старый товар
Сохрани views.py, проверь маршрут главной и обнови браузер. В нашем примере показывается последний добавленный товар; при изменении цены редактируй именно его.

Как товар попадает на страницу

Этот разбор связывает файлы проекта с тем, что ты видишь в браузере.

  1. Ты открываешь главную страницу. Django ищет подходящий адрес в urls.py и вызывает функцию home.
  2. home находится в catalog/views.py. Она обращается к модели Product, описанной в catalog/models.py, и получает товар из базы.
  3. Функция собирает строку с названием и ценой. HttpResponse возвращает её браузеру.

Ранее миграции из catalog/migrations/ создали таблицу для товаров. Регистрация в catalog/admin.py позволила добавлять и менять товары через админку. При обычном открытии главной миграции заново не выполняются.

Проверь понимание: ты изменил цену товара в админке и обновил главную. Откуда home возьмёт новую цену? Объясни, почему не нужно менять строку с ценой в views.py.
